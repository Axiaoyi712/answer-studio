# 六项改进：使用与验收

服务 0.10.0，Edge 扩展 0.9.0。现有商品资料、规则、审核状态和发布版本保留，不需要重新导入知识。

## 更新后先做这三步

1. 保存尚未提交的编辑，在本地工作台按 Ctrl + F5。
2. 打开 `edge://extensions`，重新加载“知答 · 小红书智能客服”，确认版本 0.9.0，再刷新小红书聊天页。
3. 从扩展打开客服，核对业务并启动接待。工作台“05 接待概览”应出现账号心跳；接待正常绿色、故障红色，暂停或等待使用中性色。保留原有独立人工窗口、恢复接待、悬浮球和发送防重。

## 1. 知识缺口有完整处理阶段

位置：工作台“01 知识与训练”→“知识缺口与冲突”。

- 缺少资料的人工记录自动形成独立缺口，在线记录以后归档也会继续保留缺口。服务故障、发送异常、个人订单处理等不列为知识缺口。
- 可以在对话建库里回答，也可以手动添加知识，再在缺口卡片关联已有知识；错误关联可以解除。
- 状态依次为待补充、待审核、待发布、待验证。用原问题验证当前正式版本，引用和期望关键词均通过，且没有剩余未答问题，才显示验证通过。
- 验证通过会自动生成回归题；正式知识、规则或关联关系变化后，原检查不能直接代表新内容通过。删除、撤回审核、停用或失效会重新打开相应缺口。
- 知识缺口验证不改变客户的人工待办状态。人工接待与知识建设分别完成，防止把“已存草稿”误算成客户已经解决。

实际验收：用测试号问一条缺少资料的问题 → 在建库对话补充 → 确认缺口仍显示待审核 → 审核并发布 → 点击“用原问题验证已发布版本” → 验证通过后默认列表隐藏，勾选“显示验证通过的缺口”可回看。

## 2. 对话建库保存主题进度

位置：“对话建库”右侧展开“建库主题进度”。

长期保存七类主题：主营类目、规格用途、价格单位、购买、运费发货、售后、例外。模型根据经营者原话更新；也可手动选择状态并保存备注。暂不清楚、暂不提供、不适用会作为后续访谈背景，避免反复追问。“已提供资料”仅表示这个主题有资料，不能等同所有商品全部完整。

实际验收：说“运费暂时不清楚，先问售后”，刷新后查看进度与备注仍保留。补充运费后，确认更新进度，并核对自动整理的待审知识。模型可能漏记或理解错误，可直接手动修正进度和资料。

## 3. 冲突、有效期与紧急停用

位置：知识清单每条下方“有效期与备注”“紧急停用”；同商品同问法的冲突显示在“知识缺口与冲突”。

- 有直接冲突时，发布被阻止。核对来源后选择“保留此条，撤回同组其他审核”，再检查发布差异。
- 有效期可留空；失效日期到达后不再参与回答。生效、失效和紧急停用会立即过滤正式版本及旧版本中的该条知识，原发布快照不被改写。
- 模型生成完成及网页发送前检查知识版本签名。生成期间资料被停用或修改生效，旧答案不继续发送，必要时保留草稿供核对。
- “撤回审核”“删除草稿”仍用于下一次发布，不能替代紧急停用。需要立刻阻止正式引用，应先停用。
- 发布前自动运行已有回归题。也可到“03 版本与部署”维护题目、关键词和应引用的知识，每次最多 50 题。题目或知识变化需重新检查；失败不会发布。

实际验收：在测试业务添加两条同商品、同问题、不同价格，均审核 → 发布应被阻止 → 选择保留正确项 → 运行回归检查后发布。再停用一条正式知识，在发布模式测试确认不能继续引用；恢复后再核对。

冲突检查覆盖同商品、相同或交叉别名问法的直接矛盾，尚不能发现全部语义冲突。回归验证检查可用引用、关键事实及指定关键词，不等同完整语义证明；重要答案仍需人工抽查。

## 4. 长对话与多个问题

按业务、账号、客户分别保存已观测的消息，保留最近 120 条及长期型号、最近需求偏好。当前明确换型号时采用新型号；顾客再问“刚说那款多少钱”可沿用此前选择。历史商品价格不作为当前事实依据，仍须引用当前有效知识。只记录观察到的客户消息和页面消息，不把尚未发送的生成稿当成已发送。

一次问几个问题时，逐项检索。能回答的先发送；模型明确列出的未答事项单独进入人工，等待用语仍为“不好意思，请稍等”。同一待办不反复发等待消息，其他客户继续接待。多问题划分仍依赖模型判断，并非能保证识别所有遗漏。

实际验收：在测试业务提供一款笔和一种纸的真实测试资料，连续咨询型号、价格、包装，再问“刚说那款多少钱”。询问“这支笔多少钱，能刻字吗”，其中刻字规则不提供，预期先回答价格，刻字问题进入人工；另一测试号此时问已知问题，应继续自动回复。

## 5. 独立运行监控

位置：“05 接待概览”；异常会尝试通过 Edge 桌面通知提醒。

接待页面约每 15 秒报告心跳、最近读取/生成/发送时间及待办数量，不携带消息正文。扩展后台每分钟独立检查：超过 2 分钟没有页面心跳或成功读取、问答连续失败、待回复超过 5 分钟无生成/发送进展、本地服务无法连接。重复同一异常不反复提醒，恢复后再次异常可再提醒。通知权限关闭时，面板和概览仍可查看状态。

实际验收：先启动接待并确认绿色状态，在保存工作后关闭专用接待标签页，等待下一次检查，应收到异常通知；或停掉本地服务后观察扩展通知。恢复服务及页面后核对心跳。手动暂停后不会被当成仍在运行的异常。

电脑休眠、Edge 完全退出、网络中断或平台登录/限制都会影响接待；浏览器后台监控不能代替独立的全天候服务器，也不能保证平台不限制账号。平台出现限制仍按原流程停止发送并人工处理。

## 6. 接待概览与抽查

“05 接待概览”支持 7/30 天，打开时每 15 秒刷新，显示在线任务样本、已自动回复、待人工、标记完成、待办原因、重复问题、等待时长及知识闭环。等待从任务首次记录开始计算，不随心跳刷新归零。

“04 接待记录与归档”每条在线记录可标记确认正确、回答有误、已确认解决、尚未解决。只有人工抽查样本计算正确率，没有样本显示未抽查；“发出回复”“关闭人工窗口”“标记完成”均不自动视为已经解决。

接待模型的请求数、输入/输出 tokens 和平均问答耗时单独统计，实验室和建库测试不混入。未配置服务商单价时不推算金额。

统计范围为所选期间仍在线的任务最新状态，不是所有消息总量；归档不计入在线样本。重复问题按规范化文本聚合，不等同语义聚类。历史已归档且未提取的旧缺口不会自动重新导入；已存在的本轮缺口长期保留。长期需求记录和知识缺口存于本地 SQLite，跨设备不会自行同步。

## 本轮验证记录

隔离环境使用合成商品和模拟页面，不向小红书真实客户发送验收消息。

本轮通过 127 项 Node 测试、52 项自动接待浏览器检查、35 项工作台浏览器检查，以及下列真实模型场景。原有 2 个业务空间、130 条知识、10 个发布版本和建库对话已核对保留；验收汇总见 `work/business-quality/acceptance.json`。

- Node 回归测试：`npm.cmd test`。
- 工作台浏览器操作：`node scripts/verify-workbench-browser.mjs`，截图和结果在 `work/workbench-browser/`。
- 自动接待浏览器场景：`node scripts/verify-inbox-browser.mjs`，结果在 `work/inbox-browser/result.json`。
- 真实模型：`scripts/verify-business-quality-model.mjs` 的 3 个新场景，`scripts/verify-answer-quality-model.mjs` 的 14 个商品场景，`scripts/verify-site-knowledge.mjs --live` 的 24 个通用场景，以及 `scripts/verify-interview-model.mjs` 的 7 轮访谈。用 `node --env-file-if-exists=.env` 运行；结果在对应 `work/` 子目录。
- 更新前的数据库备份和升级后核对回执在 `work/business-quality/latest-backup.json`、`work/business-quality/deployment.json`；备份文件在 `data/backups/`。真实业务知识未混入测试资料。
